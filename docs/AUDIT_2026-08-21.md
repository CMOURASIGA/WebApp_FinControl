# Auditoria 7Finance - 2026-08-21

## Escopo auditado

Branch `main` do repositório `CMOURASIGA/WebApp_FinControl`, comparada conceitualmente com o padrão atual da suíte Consult Services e do 7Commander.

## Resumo executivo

O 7Finance possui uma base funcional consistente e já cobre grande parte do domínio financeiro empresarial pretendido. Não é necessário reconstruir o produto.

A prioridade deve ser:

1. convergir frontend/UX para o padrão da suíte;
2. consolidar autorização por capabilities;
3. preparar multiempresa/tenant;
4. implementar Orion de forma server-side e segura;
5. adicionar testes formais dos cálculos e fluxos financeiros.

## Matriz de situação

| Área | Situação | Observação |
|---|---|---|
| Dashboard | Bom | KPIs relevantes já existem, falta drill-down e padronização de estados |
| Projetos e receitas | Bom | Fluxo funcional, formulário de novo projeto deve ser revisto como página/drawer conforme complexidade |
| Custos e despesas | Bom | CRUD e auditoria existem, inclusão deve migrar para drawer |

| White label | Parcialmente alinhado | Existe e possui preview, deve evoluir para tenant e padrão único da suíte |
| Autorização backend | Boa base | RLS por papel já existe |

## Achados de frontend

### Conforme

- Sidebar responsiva.
- Header persistente.
- Navegação organizada por áreas.
- Componentes base reutilizáveis.
- Uso consistente de Tailwind.
- White label aplicado ao shell/login.
- Modais já usados para ações e edição em alguns fluxos.

### Ajustar

- Criar Drawer padrão.
- Migrar cadastros curtos para Drawer.
- Modal central para confirmação, aviso, ação crítica e histórico curto.
- Página exclusiva para fluxos grandes.
- Criar PageHeader e padrões de ação primária/secundária.
- Criar estados padronizados de loading, empty, error e permission denied.
- Criar DataTable/ResponsiveList comum.
- Reduzir formulários sempre abertos em páginas operacionais.
- Inserir launcher global da Orion.

## Achados funcionais

### Pontos fortes

- Motor de cálculo isolado em `motorCalculo.ts`.
- Parâmetros tributários e distribuição são vigentes e não hardcoded.
- Receita preserva snapshot da regra aplicada.
- Retirada possui validação de saldo no banco.
- Fechamento mensal ocorre por RPC transacional.
- RLS evoluiu para perfis `admin`, `financeiro`, `socio` e `consulta`.
- Novos logins são criados inativos, evitando acesso automático.
- CRUD e histórico de despesas/investimentos estão presentes.
- Indicadores de ROI, break-even, MRR e ARR existem.

### Riscos / gaps

1. O README está parcialmente desatualizado em relação às migrations mais novas.
2. A UI continua tomando poucas decisões por perfil e pode apresentar ações que o banco depois recusa.
3. Não há camada de capabilities centralizada.
4. Não há tenant/empresa no desenho operacional principal.
5. Não há suíte de testes automatizados declarada no package.json.
6. Não há Orion.
7. O fechamento não possui etapa visual formal de confirmação/readiness.
8. Algumas páginas executam muitas consultas em sequência no browser e devem ser observadas para escala.
9. O dashboard precisa permitir rastrear a origem de um KPI.
10. A branch `develop` não existe no 7Finance no momento auditado.

## Prioridade de execução

### P0 - Segurança e governança

- capabilities frontend/backend;
- testes RLS por perfil;
- preparar tenancy;
- revisar permissões de todas as RPCs e services.

### P1 - UX padrão suíte

- Drawer;
- PageHeader;
- DataTable/ResponsiveList;
- estados padrão;
- confirmação central;
- refatorar cadastros abertos.

### P1 - Orion

- Edge Function/API segura;
- launcher e painel;
- ferramentas somente leitura;
- contexto financeiro;
- auditoria de uso.

### P2 - Qualidade

- testes do motor financeiro;
- testes de integração das RPCs;
- testes de regressão de fechamento;
- README e documentação técnica atualizados.

### P2 - SaaS

- empresa/tenant;
- usuários por empresa;
- licenciamento futuro com Consult Hub;
- white label por empresa.

## Decisão recomendada

Manter a base atual e evoluir por refatoração incremental. O domínio funcional já possui valor suficiente para não justificar reescrita. A próxima implementação deve começar por segurança/capabilities e padrão de frontend, seguida da Orion.
